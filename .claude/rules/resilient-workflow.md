# 韧性执行工作流（AutoResearchClaw 适配）

> 来源：AutoResearchClaw (arxiv 2605.20025) — AI 科研 Agent 失败处理方法论
> 本文档为行为约束，与 debug/review/complex 等主工作流联动使用
> 优先级：高于 workflows.md 中的默认行为

---

## 一、自愈执行（Self-Healing Execution）

**失败≠终止。任何执行失败，先记录失败签名，再诊断根因，再修复。不得在未诊断的情况下盲目重试。**

### 失败签名分类

| 类型 | 描述 | 默认处理 |
|------|------|---------|
| `SYNTAX` | 语法/类型/编译错误 | 直接修复，1轮内解决 |
| `BOUNDARY` | 边界条件、断言失败 | 诊断业务逻辑，走 Lite 流程 |
| `DEPENDENCY` | 依赖缺失、环境问题 | 考虑调整方案，走 Full 流程 |
| `LOGIC` | 逻辑错误、语义错误 | 回退到设计层，可能触发 Pivot |

### 执行流程

```
步骤 1：记录失败签名
├─ 错误类型：SYNTAX / BOUNDARY / DEPENDENCY / LOGIC
├─ 错误位置：文件:行号 或 步骤名称
├─ 错误上下文：触发条件、输入数据、系统状态
└─ 症状：用户/测试看到的现象

步骤 2：诊断→修复→验证（最多 3 轮）
├─ 诊断：根据失败签名定位根因（不是症状）
├─ 修复：针对性补丁，不是盲改
├─ 验证：仅运行失败的测试，不全量跑
└─ 超过 3 轮未修复 → 进入 Pivot/Refine 决策

步骤 3：记录到 Lesson Store
└─ 写入 .claude/memory/lessons/ 对应主题文件
```

### 静态检查门（执行前拦截）

在消耗执行预算前，先做低成本检查：
- [ ] 是否存在两个功能完全重复的函数/模块？
- [ ] 是否有硬编码的魔法数字或期望值？
- [ ] diff 范围是否超出本次任务边界？
- [ ] 是否误修改了不该动的文件（配置、锁文件、.gitignore）？
- [ ] 任务目标是否足够明确？（不明确则先澄清，不执行）

检查通过后，输出："Pre-flight passed，开始执行。"

## 二、Pivot / Refine 决策

**连续 3 轮修复失败，或判断当前方向根本性错误时，必须停下结构化决策。**

### 决策框架

```
评估当前状态：

结果符合预期？
└─ 是 → PROCEED：继续推进

方向正确但实现有问题？
└─ 是 → REFINE：
      ├─ 明确保留哪些、重做哪些
      ├─ 估算修复成本（时间/行数）
      └─ 成本可控 → 继续
         成本过高 → 降级为 P2 或拆分到后续迭代

方向根本性错误？
└─ 是 → PIVOT：
      ├─ 记录失败原因（为什么方向错了）
      ├─ 回退到设计阶段
      ├─ 新方案必须回答：上次为何失败？这次如何规避？
      └─ 检查是否需要回滚已提交代码
```

### 汇报格式

```
## Pivot/Refine 决策

**当前状态**: [已完成什么，卡在哪里]
**失败原因**: [方向错误 / 实现问题 / 环境问题]
**建议决策**:
  - [ ] PROCEED（继续）
  - [ ] REFINE（修复后继续，预估成本：___）
  - [ ] PIVOT（换方向，回退到：___）

等待确认...
```

## 三、SmartPause（高不确定性暂停）

**自动识别高风险信号，在扩大错误前主动暂停。**

### 触发阈值

| 信号 | 阈值 | 严重度 |
|------|------|-------|
| 连续失败次数 | ≥ 3 次 | 高 |
| 改动行数 | > 200 行且任务未完成 | 中 |
| 跨模块/目录修改 | ≥ 3 个不同模块 | 中 |
| 需求边界扩大 | 出现计划外改动 | 高 |
| 结果语义异常 | 输出全部相同/全为零/全为空 | 高 |
| 修改了关键基础设施 | 配置/Schema/接口定义 | 高 |

### 汇报格式

```
⏸ SmartPause — 高不确定性

**触发原因**: [具体信号 + 数据]
**当前进度**: [已完成 X / 总量 Y]
**风险**: [继续执行的最坏结果]
**建议**:
  A. 继续（说明理由）
  B. 先修复 ___ 再继续
  C. 回退，换方向

等待指令...
```

## 四、验证注册表（Verified Registry）

**结论必须有证据。所有报告中的数据必须来自实际运行输出。不得使用估算值、预期值或未运行的假设值。**

### 核心规则

```
禁止：
❌ "测试通过了"（无具体输出）
❌ "性能提升了"（无前后对比数据）
❌ "修复了 bug"（无复现/修复对比）
❌ 在报告中使用未经运行的估算数字

要求：
✅ 引用实际运行输出
✅ 性能变更必须有前后测量值
✅ Bug 修复必须附复现步骤 + 修复后回归结果
```

### 反向校验

报告完成后，抽查 2-3 个关键数值是否与运行记录匹配。不匹配 → 报告必须修正。

## 五、多角色审查（Multi-Role Review）

**审查不是走形式，Skeptic 角色必须独立评估，不得因"看起来没问题"就跳过。**

### 角色定义

| 角色 | 核心问题 | 适用场景 |
|------|---------|---------|
| **Builder** | 实现是否完整？功能是否可用？ | 所有审查 |
| **Skeptic** | 边界条件？性能隐患？隐式假设？ | 所有审查 |
| **Architect** | 模块耦合？接口契约？可维护性？ | 架构/复杂改动 |

### 审查规模规则

| diff 大小 | 审查方式 |
|-----------|---------|
| ≤ 100 行 | 单轮自检，不需要多角色 |
| 100-200 行 | Builder + Skeptic 双角色 |
| > 200 行 | 三角色完整审查（此类改动应先拆分） |

### 裁决规则

- Builder 与 Skeptic 一致 → 通过
- 有分歧 → 用测试数据裁决
- Skeptic 发现 P0/P1 → 必须修复后重新审查，不得直接合并

## 六、Lesson Store（跨任务经验积累）

**修复完成后，将失败签名写入 Lesson Store。任务开始前，检索相关历史教训。**

### 存储路径

```
.claude/memory/lessons/
├── syntax.md        # 语法/类型错误
├── boundary.md      # 边界条件
├── dependency.md    # 依赖/环境
├── logic.md         # 逻辑/设计错误
└── patterns.md      # 通用模式（Review 发现）
```

### 每条记录格式

```markdown
## [YYYY-MM-DD] [场景简述]

**失败类型**: SYNTAX | BOUNDARY | DEPENDENCY | LOGIC
**症状**: [观察到的现象]
**根因**: [一句话说清楚]
**修复方案**: [具体做法 + 相关 commit/文件]
**教训**: [下次如何避免]
**相关文件**: [路径列表]
**权重衰减**: 写入日期后 7 天高权重，30 天后低权重
```

### 自动注入规则

- 任务开始 → Grep `.claude/memory/lessons/` 搜索相关教训
- Debug 完成 → 写入失败签名到对应主题文件
- Review 发现问题 → 写入 patterns.md
- 成功且无新教训 → 不写入（保持文件简洁）

## 七、CoPilot 介入策略

**在任务开始时声明本次使用哪种介入模式，在高杠杆节点主动暂停等待确认，不得静默推进关键决策。**

### 高杠杆介入点（必须等待确认）

| 节点 | 原因 |
|------|------|
| 任务/需求定义 | 方向错了，后续全部返工 |
| 方案/架构评审 | 结构问题越晚发现越贵 |
| 首次执行结果 | 验证基础假设是否成立 |
| 合并/发布前 | 最终质量门 |

### 低杠杆自动放行

- 语法修复、格式调整 → 自动
- 测试补充 → 自动
- 文档/注释更新 → 自动
- 已有明确规范的重复性操作 → 自动

### 模式选择

| 场景 | 模式 | 介入次数 |
|------|------|---------|
| 日常小修（< 50 行） | Full-Auto | 0 |
| 单模块功能开发 | Gate-Only | 2-3 |
| 跨模块/复杂功能 | CoPilot | 4-6 |
| 架构级变更 | Step-by-Step | 全程 |
