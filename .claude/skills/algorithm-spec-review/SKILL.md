# 算法规格审查（7 阶段审计工作流）

## ⛔ MANDATORY GATES (read before proceeding)

> 执行前必须 echo-back 本块。未输出 = 未开始。

| # | 门禁点 | 位置 | 通过条件 |
|---|--------|------|----------|
| G1 | 读取全部 7 个阶段标题 | 全文 | 输出：发现→规范化→规格IR→代码IR→对齐IR→分歧分类→报告 |
| G2 | 置信度阈值检查 | 对齐阶段 | 低于阈值条目标记为 [MANUAL_VERIFY] |
| G3 | 反幻觉校验通过 | 最终报告 | 列出置信度 <0.5 和 UNVERIFIABLE 条目 |
| G4 | Echo-Back | 执行前 | 输出本表全部 G1-G3 |

审查算法规格包时，把规格、配置、参考实现、测试材料和样本证据放到同一张审查表里，才能发现真正会落地出错的断层。

核心原则：没有代码映射和证据支撑的规格结论，不算闭环。每一条对齐判断都必须附带置信度评分，低于阈值的条目标记为需要人工验证。

## 适用场景

典型信号：
- 算法规格包需要与代码实现核对一致性
- 规格文档（PRD/设计文档）与实际代码的偏差检测
- 安全/合规要求下的规格合规审计
- 用户让你"审查方案""评估是否可落地""核对文档和代码是否一致"
- 目录里同时存在方案文档、参数配置、参考实现、测试文档、样本或验证报告
- 涉及阈值、档位、材质分类、控制节流、输出字段、错误码、参数默认值

不适用：
- 纯代码修 bug，没有规格或验证材料
- 纯文档润色，不需要检查实现和证据

## 7 阶段审计工作流

### Stage 1: Discovery — 发现与收集

目标：明确审查边界，列出完整的审查清单。

1. 识别规格文档（PRD、设计文档、接口文档、参数配置文件）
2. 识别代码实现文件（核心算法、配置解析、辅助模块）
3. 识别测试和证据材料（测试脚本、测试报告、样本数据、日志）
4. 列出审查范围：
   - 文件清单（路径 + 职责）
   - 预期覆盖的规格条目数
   - 明确排除的范围及原因

输出：`Discovery 清单`（文件列表 + 预期规格覆盖范围）

### Stage 2: Normalization — 规格规范化

目标：从自然语言文档中提取可验证的断言。

1. 从规格文档逐段提取"必须成立"的断言（assertions），写成可核对的句子
2. 每个断言标记：
   - **来源段落**：文档路径 + 章节/行号
   - **类型**：功能（F）/ 性能（P）/ 安全（S）/ 边界（E）/ 配置（C）
   - **优先级**：P0（必须）/ P1（应该）/ P2（建议）
3. 对模糊断言标注 `[AMBIGUOUS]`，附模糊原因，不自行解读
4. 去重：合并重复断言，保留最具体的表述

输出：`规格断言列表`（每条含 id、原文、来源、类型、优先级）

### Stage 3: Spec-IR — 规格中间表示

目标：将断言转化为结构化的中间表示，便于后续与代码对齐。

1. 将每个断言转化为结构化 IR：
   ```
   {
     id: "SPEC-001",
     assertion: "当输入图片宽度 > 4096px 时，必须返回错误码 IMG_RES_EXCEEDED",
     type: "E",
     priority: "P0",
     expected_behavior: "返回错误码 IMG_RES_EXCEEDED，不执行合并",
     verification_method: "构造 4097px 宽度图片作为输入，检查返回值"
   }
   ```
2. 每条 IR 必须包含可执行的验证方法（而非笼统的"检查代码"）
3. 标记无法自动验证的条目为 `[MANUAL_VERIFY]`
4. 统计：总断言数 / 各类型分布 / 各优先级分布

输出：`Spec-IR 列表`

### Stage 4: Code-IR — 代码中间表示

目标：从代码中提取实际行为，形成与 Spec-IR 可对齐的结构。

1. 从代码中提取实际行为：
   - 函数签名与调用关系
   - 数据流（输入 → 处理 → 输出）
   - 边界处理（空值、极值、异常格式）
   - 错误处理（异常类型、错误码、返回值）
   - 配置读取（默认值、阈值、参数来源）
2. IR 格式：
   ```
   {
     id: "CODE-001",
     code_location: "merger.py:merge_images():L45-L52",
     actual_behavior: "当宽度 > MAX_WIDTH(4096) 时抛出 ValueError('resolution exceeded')",
     edge_cases: "空图片返回 None",
     error_handling: "try/except 捕获 UnidentifiedImageError"
   }
   ```
3. 标记无法从代码确认的行为 `[UNVERIFIABLE]`，说明原因（如：行为依赖运行时状态）
4. 标记代码中存在但规格未提及的行为 `[EXTRA_BEHAVIOR]`

输出：`Code-IR 列表`

### Stage 5: Alignment-IR — 对齐映射

目标：将 Spec-IR 与 Code-IR 逐条对齐，识别匹配与分歧。

1. 将 Spec-IR 与 Code-IR 逐条对齐：
   - 精确匹配：Spec 断言与 Code 行为一一对应
   - 多对一：多条 Spec 断言对应同一段代码
   - 一对多：一条 Spec 断言分散在多段代码中
2. 每个对齐条目标记状态：
   - `ALIGNED`：规格与代码行为一致
   - `PARTIAL`：部分一致，存在差异
   - `MISSING`：规格要求但代码中未找到对应实现
   - `CONFLICT`：规格与代码行为明确矛盾
   - `EXTRA`：代码中存在但规格未提及的行为
3. 计算对齐覆盖率：
   - 总断言数
   - 已对齐数（ALIGNED）
   - 对齐率 = ALIGNED / 总断言数

输出：`Alignment-IR 列表`（含对齐状态 + 覆盖率统计）

### Stage 6: Divergence Classification — 分歧分类

目标：对每个非 ALIGNED 条目进行分类和置信度评分。

分歧类型：
- `SPEC_MISSING`：代码中存在的行为，但规格文档未覆盖（遗漏的规格）
- `CODE_MISSING`：规格要求的断言，但代码中未实现（遗漏的实现）
- `BEHAVIOR_MISMATCH`：规格与代码行为不一致（规格说 A，代码做 B）
- `AMBIGUITY`：规格模糊导致多种解读，无法确定代码是否符合

置信度评分规则（0-1）：
- **1.0**：证据确凿（规格原文与代码逻辑可直接对比，无歧义）
- **0.7-0.9**：高度可信（有明确的代码路径可追溯，但涉及间接逻辑）
- **0.4-0.6**：需要人工确认（规格或代码存在模糊，AI 判断可能有偏差）
- **<0.4**：可能是误报（信息不足或理解可能存在偏差）

每个分歧条目格式：
```
{
  divergence_id: "DIV-001",
  spec_ir_id: "SPEC-003",
  code_ir_id: "CODE-005",
  type: "BEHAVIOR_MISMATCH",
  confidence: 0.85,
  description: "规格要求返回错误码 IMG_RES_EXCEEDED，代码实际抛出 ValueError",
  evidence: "merger.py:L47 抛出 ValueError('resolution exceeded')",
  suggested_fix: "修改代码返回统一错误码，或修改规格文档匹配异常类型"
}
```

输出：`分歧列表`（含分类 + 置信度 + 建议）

### Stage 7: Report — 审查报告

目标：输出结构化审查报告，按优先级排列，便于人工决策。

报告格式：

```markdown
# 算法规格审查报告

## 审查范围
- 规格文档: [文件列表]
- 代码文件: [文件列表]
- 测试/证据: [文件列表]

## 摘要
- 规格断言数: X
- 已对齐 (ALIGNED): Y (Z%)
- 分歧总数: W
  - SPEC_MISSING: A（规格遗漏）
  - CODE_MISSING: B（实现遗漏）
  - BEHAVIOR_MISMATCH: C（行为不一致）
  - AMBIGUITY: D（规格模糊）

## 对齐覆盖率
| 类型 | 总数 | ALIGNED | PARTIAL | MISSING | CONFLICT | EXTRA |
|------|------|---------|---------|---------|----------|-------|
| 功能 | X | Y | Z | ... | ... | ... |
| 性能 | X | Y | Z | ... | ... | ... |
| 安全 | X | Y | Z | ... | ... | ... |
| 边界 | X | Y | Z | ... | ... | ... |
| 配置 | X | Y | Z | ... | ... | ... |

## 高置信度分歧（≥0.7，需优先处理）
| ID | 类型 | 置信度 | 描述 | 建议修复 |
|----|------|--------|------|----------|
| DIV-001 | BEHAVIOR_MISMATCH | 0.85 | ... | ... |

## 低置信度分歧（<0.7，需人工确认）
| ID | 类型 | 置信度 | 描述 | 需确认事项 |
|----|------|--------|------|------------|
| DIV-003 | AMBIGUITY | 0.45 | ... | ... |

## 反幻觉校验
- 以下条目需要人工验证：[列出置信度 <0.5 的条目]
- 原因：[说明为什么 AI 判断可能不准确]
- 未验证条目：[列出标记为 UNVERIFIABLE 的条目]

## Mismatch Map（规格 → 代码断层映射）
| 规格断言 | 代码位置 | 对齐状态 | 备注 |
|----------|----------|----------|------|
| SPEC-001 | CODE-001 | ALIGNED | - |

## Next Actions（优先级排序）
1. [P0 分歧修复建议]
2. [P1 分歧修复建议]
3. [补充测试/证据建议]
```

## 反幻觉规则

- 置信度 <0.5 的条目**必须**标记为 `[NEEDS_HUMAN_VERIFY]`
- 不基于推测填充缺失的对齐：找不到对应代码就标记 `MISSING`，而非猜测
- 明确标注"代码中无法确认"（`[UNVERIFIABLE]`）而非自行编造行为描述
- 对模糊规格标注 `[AMBIGUOUS]` 并列出可能的解读，不选择其中一种作为结论
- 证据引用必须包含具体文件路径和行号，不可引用不存在的位置
- 置信度评分基于可追溯的证据量，而非主观感觉

## 约束

- 审查范围限于提供的规格文档和代码文件
- **不修改代码**，只输出审查报告
- 对模糊规格标注 `[AMBIGUOUS]` 而非自行解读
- 单条分歧必须有明确的证据链（规格原文 + 代码位置）
- 报告中的统计数字必须与详细条目一致，不可虚报
