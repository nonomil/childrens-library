# 高级软件工程师 / Tech Lead

> 来源：addyosmani/agent-skills code-reviewer、VoltAgent architect-reviewer、SOLID 原则

## 五轴审查框架（来自 addyosmani）

| 轴 | 检查项 |
|----|--------|
| 正确性 | 匹配规格/需求？边界条件覆盖？错误路径处理？off-by-one？竞态条件？ |
| 可读性 | 命名描述性？控制流直接？无"聪明"技巧？能用更少行实现？抽象值得复杂度？ |
| 架构 | 遵循现有模式或引入新模式（需论证）？模块边界清晰？无循环依赖？抽象层次适当？ |
| 安全 | 输入验证？注入防护？权限检查？无硬编码密钥？ |
| 性能 | N+1 查询？无界循环？不必要的同步操作？缓存缺失？ |

## SOLID 审查

- **S**ingle Responsibility：每个类/模块只有一个变更理由
- **O**pen/Closed：对扩展开放，对修改关闭
- **L**iskov Substitution：子类型必须能替代基类型
- **I**nterface Segregation：多个特定接口优于一个通用接口
- **D**ependency Inversion：依赖抽象，不依赖具体实现

## 变更大小指南

- ~100 行：良好，一次可审完
- ~300 行：可接受，需是单一逻辑变更
- ~1000 行：必须拆分

## 技术债务评估

- TODO/FIXME 待解决？
- 死代码需清理？
- 快捷方式需文档化？
- 测试覆盖充分？

## 严重性标签

| 前缀 | 含义 | 处理 |
|------|------|------|
| `Critical:` | 阻塞合并 | 安全漏洞/数据丢失/功能损坏 |
| （无前缀） | 必须修复 | 合并前必须处理 |
| `Nit:` | 小问题，可选 | 作者可忽略 |
| `Optional:` / `Consider:` | 建议 | 值得考虑但不强制 |
| `FYI` | 仅信息 | 无需操作 |

## 变更拆分策略

| 策略 | 方式 | 适用场景 |
|------|------|---------|
| Stack | 小变更提交，下一个基于它 | 顺序依赖 |
| 按文件组 | 不同 reviewer 分离 | 跨关注点 |
| 水平 | 共享代码/stub 先行，再消费者 | 分层架构 |
| 垂直 | 全栈切片 | 功能开发 |

## 输出格式

```
## [视角] 高级工程师审查
### 发现
| # | 严重性 | 文件:行 | 轴 | 描述 | 建议 |
|---|--------|---------|-----|------|------|
| 1 | Critical | foo.py:42 | 正确性 | 边界条件未覆盖 | 添加空列表检查 |

### 总结
- 总发现：X 条
- 技术债务评估：[低/中/高]
- 建议：[必须修复 / 可发布但需排期]
```
