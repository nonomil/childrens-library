# 算法规格审查

审查算法规格包时，把规格、配置、参考实现、测试材料和样本证据放到同一张审查表里，才能发现真正会落地出错的断层。

核心原则：没有代码映射和证据支撑的规格结论，不算闭环。

## 何时使用

典型信号：
- 用户让你"审查方案""评估是否可落地""核对文档和代码是否一致"
- 目录里同时存在方案文档、参数配置、参考实现、测试文档、样本或验证报告
- 涉及阈值、档位、材质分类、控制节流、输出字段、错误码、参数默认值

不适用：
- 纯代码修 bug，没有规格或验证材料
- 纯文档润色，不需要检查实现和证据

## 审查对象

| 类别 | 常见文件 | 重点问题 |
|------|---------|---------|
| 规格文档 | 方案 `.md`、计划、审查结论 | 断言是什么，成功标准是什么 |
| 配置 | 参数配置文件、参数表 | 默认值、阈值、档位语义是否一致 |
| 参考实现 | `src/`、核心算法文件 | 规格是否真的落地 |
| 测试材料 | 测试文档、脚本、报告 | 有没有覆盖关键分支、边界 |
| 样本证据 | 数据集、截图、日志 | 规格结论有没有证据支撑 |

## 工作流

### 1. 先抽规格断言

从文档中提炼"必须成立"的断言，写成可核对的句子。

### 2. 再做代码映射

去配置和代码里逐条找对应实现。文档有说法但代码找不到落点，标为断层。

### 3. 用测试和样本做证据校验

- 是否有测试覆盖该断言
- 样本或报告是否支持这个阈值/判断逻辑

### 4. 输出 findings

按严重程度排序，每条写明出处，明确说明风险。

## 审查结论最低结构

| 输出 | 要求 |
|------|------|
| Findings | 按严重度排序，可追溯到文件或证据 |
| Mismatch Map | 规格 → 配置 → 代码 → 证据的断层映射 |
| Missing Validation | 哪些关键断言没有测试或样本支撑 |
| Next Actions | 先改什么，再补什么验证 |
