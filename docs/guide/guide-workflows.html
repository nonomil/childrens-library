工作流详解

8 种场景工作流 + 全局常量，按优先级自动路由，匹配即停止

工作流路由机制

收到任务后，Claude Code 按固定优先级逐条匹配场景路由表。匹配即停止，不会同时走两个工作流。

路由优先级（从高到低）：Debug > Code Review > C++ Build > C++ Test > Research > Largebase > Parallel > Complex > Simple
匹配规则：用户描述中命中触发词 → 读取对应工作流文档 → 按文档执行

简单模式 vs 复杂模式

简单模式

（5 条全满足）
✓ 涉及文件 ≤ 3 个
✓ 预估 diff ≤ 200 行
✓ 需求明确，无歧义
✓ 单模块内，不跨模块
✓ 不触及高风险文件

流程：讨论 → 实现 → 单轮自查 → 提交

复杂模式

（任意 1 条不满足）
触发对应工作流，走完整流程

流程：扫描 → Plan → 审查 → Steps → 开发 → Review

模式升级触发（全程检查）：
diff >200 行 / 需修改 >3 文件 / 跨模块依赖 / Review >3 轮仍有问题

Debug 工作流

优先级 1 描述 bug/错误/测试失败 → 强制走此流程。先写回归测试再修复，防止修了旧 bug 引新 bug。

Phase 0：症状收集 — 把"不好使"翻译成可操作信息

创建 Bug 卡片，包含：现象描述、稳定复现步骤、预期行为、实际行为、环境信息（OS/版本/数据量）。

Phase 1：快速排查（≤5 分钟）

git 检查（最近改动）、环境问题排查（依赖/配置/端口）。5 分钟内能定位则直接修，不进后续流程。

Phase 2：Codex 扫描定位根因

调用 Codex 长上下文分析，扫描代码库定位根因。输出：疑似根因、影响范围、置信度。

Phase 3：CC 制定修复方案

CC 交叉验证 Codex 结论，制定修复方案。严重程度 ≥P1 或跨 3+ 模块时进入 Full 模式。

Phase 4：Codex 执行修复 + Review

先写复现测试（确保 bug 能触发）→ Codex 执行修复 → 两轮 Review（CC 快速 + Codex 深度）→ 全量测试无回归。

Phase 5：根因文档记录与复盘

记录 debug 过程到 debug/[feature].md，提炼教训写入 tasks/lessons.md，追加到 .claude/memory/ 记忆系统。

Code Review 工作流

优先级 2 "review/审查/检查代码质量" → 三种场景，P0-P3 四级分类。

三种 Review 场景

场景时机关注点
Spec Review计划阶段，代码生成前方案可行性、遗漏需求、架构合理性
Code Review代码生成后P0(阻塞) / P1(修完再合) / P2(下轮) / P3(可选)
PR Review准备合并 PR 前完整 diff 审查、兼容性、文档同步

Review 执行方式

diff ≤ 100 行：CC 单轮快速自查（逻辑正确性、安全性、YAGNI）

diff > 100 行或涉及核心逻辑：两轮独立审查

1
CC 快速审查：逻辑正确性、安全性、YAGNI、向后兼容
2
Codex 深度审查：边界条件、长尾情况、兼容性
3
CC 综合仲裁：有分歧 → 修复后从轮次 1 重来（最多 3 轮）

优先级 8 不满足简单标准且未命中其他路由 → 六阶段流程，最常用的工作流。

↓
2
Codex 审查 Plan：可行性、遗漏细节、边界条件
↓
3
交叉 Review：CC ↔ Codex，≥3 轮，连续 2 轮无新问题才收敛
↓
4

↓

↓

用户确认"开始开发"→ 执行代码任务

研究调研工作流

优先级 5 "调研/对比/选型/搜索" → 联网搜索 + 文档分析 + Linus 三问验证。

0
问题定义：CC 制定研究卡片（问题、范围、输出预期）
↓
1
CC 快速搜索：WebSearch 基础认知，了解技术全景
↓
2
Codex 深度读取：官方文档、README、配置文件、源码
↓
3
CC 整合 + 交叉验证：对比矩阵、Linus 三问（是真实问题？有更简单的？会破坏什么？）
↓
4
输出调研报告（可选 docs/research/）：结论、对比、推荐、风险

搜索深度选择

深度适用耗时
快速只需了解概念或确认某个用法~1 小时
标准需要对比 2-3 种方案~半天
深度技术选型、架构决策~1 天

并行开发工作流

优先级 7 任务 ≥2 且可解耦 → worktree 隔离，互不干扰。

1
解耦确认：验证任务间无共享文件依赖，每个任务边界清晰
↓
2
创建 Worktree + 分配任务：按 BRANCH_MODE 选择 temporary/bare 模式
↓
3
监控 + 合并：进度监控、按依赖顺序合并、冲突处理

并行规则

规则说明
文件边界即任务边界同一文件只能由一个任务修改
共享文件唯一 owner必须跨任务共享的文件，指定一个任务负责
合并顺序控制按 DAG 依赖顺序合并，基础模块先合
确认后合并合并前必须输出变更摘要，用户说"确认合并"才执行

C++ 编译工作流

优先级 3 "编译/build" + C++ 项目 → 自动检测 CMake/MSBuild。

0
编译方式选择：CMake（跨平台）vs MSBuild（纯 Windows）二选一
1
编译前检查：依赖、git 状态、配置、平台
2
执行编译：cmake 配置/编译 或 msbuild
3
结果检查：成功/警告/产物路径
4
可选操作：运行测试、查看警告详情、生成报告

C++ 单元测试工作流

优先级 4 "gtest/单元测试" + C++ 项目 → Google Test / CTest。

0
任务难度评估：轻量模式（仅受影响模块）vs 完整模式（全量+覆盖率）
1
测试范围确定：受影响模块 vs 全量
2
执行测试：CTest / 直接运行 GTest / 已有二进制
3
结果分析：总测试数、通过率、失败详情
4
失败处理：根因分析 → 修复策略 → 重新运行
5
报告输出：test_report.md

Git 安全约束

禁止操作（无论什么理由）：
rm -rf、git reset --hard、git clean -f、del、rd /s
git push --force（除非用户明确要求）
删除文件：一律改为移动到 tmp/ 目录，不直接删除

文件操作边界

规则说明
Scope 限制只操作 Prompt 中 Scope 指定的目录
禁止删除不删除任何文件/目录，需要清理则移动到 tmp/
禁止移动/重命名需重组目录时停下报告，等用户确认
UTF-8 强制所有文本文件读写必须显式指定 UTF-8 编码
