# 韧性开发工作流（AutoResearchClaw 适配）

> 来源：AutoResearchClaw (arxiv 2605.20025) — AI 科研 Agent 失败处理方法论
> 适配目标：将科研 Agent 的失败自愈、多角色辩论、验证注册表等方法移植到游戏开发工作流
> 本文档为辅助工作流，与 debug/review/complex 等主工作流联动使用

---

## 核心原则

| AutoResearchClaw 原则 | 开发工作流适配 | 关键收益 |
|----------------------|---------------|---------|
| 失败≠终止 | 测试失败→诊断→修复→重试，不盲跑 | 减少无效重试 |
| 多角色辩论 | Review 多角度独立审查 | 提升代码质量 |
| 验证注册表 | 测试输出=唯一真相来源 | 防止"看起来通过" |
| 失败签名 | 结构化记录错误模式 | 避免重复踩坑 |
| Pivot/Refine | 方案失败→决策：修还是换 | 减少死胡同时间 |
| SmartPause | 高不确定性时暂停等人工 | 避免错误放大 |
| CoPilot 介入 | 只在高杠杆节点要确认 | 效率与质量平衡 |

## 1. 自愈执行（Self-Healing Execution）

> 适用场景：Codex 生成代码后测试失败、编译报错、运行崩溃

### 失败不立即终止，三步处理

```
步骤 1：记录失败签名（Failure Signature）
├─ 错误类型：编译错误 / 运行时错误 / 逻辑错误 / 测试断言失败
├─ 错误位置：文件:行号
├─ 错误上下文：触发条件、输入数据、系统状态
└─ 失败模式分类：
   ├─ SYNTAX    — 语法/类型错误（通常一次修复即可）
   ├─ BOUNDARY  — 边界条件（需要理解业务逻辑）
   ├─ DEPENDENCY — 依赖/环境问题（可能需要调整方案）
   └─ LOGIC     — 逻辑错误（可能需要回退到设计层）

步骤 2：诊断→修复→验证（最多 3 轮）
├─ 诊断：根据失败签名定位根因（不是症状）
├─ 修复：针对性补丁，不是盲改
├─ 验证：仅运行失败的测试，不全量跑
└─ 超过 3 轮未修复 → 进入 Pivot/Refine 决策

步骤 3：记录到失败库
└─ 写入 .claude/memory/lessons/ 对应主题文件
```

### 与现有 Debug 流程的联动

- 命中 `SYNTAX` → 直接修复，不走完整 Debug 流程
- 命中 `BOUNDARY` → 走 Debug Lite (Phase 0-4)
- 命中 `DEPENDENCY` / `LOGIC` → 走 Debug Full (Phase 0-7)
- 超过 3 轮修复失败 → 触发下方 Pivot/Refine 决策

### 静态检查门（执行前拦截）

在消耗执行预算前，先做低成本检查：
- [ ] 新增的两个测试/函数是否逻辑完全重复？
- [ ] 是否有硬编码的魔法数字/期望值？
- [ ] 是否修改了不该改的文件（.gitignore / 配置文件）？
- [ ] diff 范围是否超出任务需求？

## 2. 多角色辩论审查（Multi-Agent Debate Review）

> 适用场景：Code Review、方案评审、复杂 Bug 根因分析

### 角色定义（游戏开发适配）

| 角色 | 职责 | 审查角度 |
|------|------|---------|
| **Builder** | 正面评估 | 实现是否完整？功能是否可用？ |
| **Skeptic** | 质疑挑战 | 边界条件？性能隐患？是否有隐式假设？ |
| **Architect** | 结构审查 | 模块耦合？接口契约？可维护性？ |

### 审查流程

```
Step 1: Builder 给出正面评估
       — 实现了什么、为什么这样做、预期效果

Step 2: Skeptic 独立质疑（不看 Builder 结论）
       — 哪里可能出错？什么输入会打破假设？
       — 性能/内存是否可接受？
       — 是否有未处理的错误路径？

Step 3: Architect 结构审查
       — 是否引入了不必要的耦合？
       — 是否遵循项目既有模式？
       — 接口是否清晰、向后兼容？

Step 4: 综合裁决
       — Builder 和 Skeptic 结论一致 → 通过
       — 有分歧 → 用测试数据裁决
       — Skeptic 发现 P0/P1 问题 → 必须修复后重新审查
```

### 与现有 Review 流程的联动

- 简单改动（diff ≤ 100 行）：CC 单轮审查即可，不需要多角色
- 中等改动（100-200 行）：CC 双角色（Builder + Skeptic）
- 大改动（> 200 行，应拆分）：完整三角色 + Codex 独立审查

## 3. 验证注册表（Verified Registry）

> 适用场景：测试报告、性能数据、用户可见的数值

### 核心规则：声称必须有运行记录支持

```
禁止：
❌ "测试通过了"（无具体输出）
❌ "性能提升了"（无前后数据）
❌ "修复了 bug"（无复现/修复对比）

要求：
✅ "3 个测试全部通过 (0.8s)，输出: ..."
✅ "帧率从 45fps → 60fps（截图对比）"
✅ "复现步骤不再触发，回归测试通过"
```

### 实施方式

1. **测试输出 = 唯一真相来源**
   - 运行测试时必须保留完整输出
   - 报告中引用的数据必须来自实际运行
   - 写作 Agent (CC/Codex) 可以读取输出，不能篡改输出

2. **截图/日志作为证据**
   - UI 变更 → 必须有前后截图对比
   - 性能变更 → 必须有 profiler 输出
   - Bug 修复 → 必须有复现→修复的日志对比

3. **数值反向校验**
   - 报告完成后，抽查 2-3 个关键数值是否与运行记录匹配
   - 不匹配 → 报告必须修正

## 4. 失败签名与 Lesson Store（跨运行经验积累）

> 已部分实现于 `.claude/memory/lessons/`，本节补充结构化方法

### 失败签名结构

每条失败记录应包含：

```markdown
## [日期] [场景简述]

**失败模式**: SYNTAX | BOUNDARY | DEPENDENCY | LOGIC
**症状**: [用户/测试看到什么]
**根因**: [一句话]
**修复**: [方案 + commit hash]
**教训**: [下次如何避免]
**相关文件**: [文件路径列表]
```

### 时间衰减权重

- 最近 7 天的失败：高权重，每次任务开始时必读
- 7-30 天：中权重，相关主题时读取
- 30+ 天：低权重，仅 grep 搜索到时加载
- 成功修复后同类问题不再复现 → 权重自然衰减

### 自动注入规则

- 新任务开始 → Grep `.claude/memory/lessons/` 搜索相关教训
- Debug 完成 → 写入失败签名到对应主题文件
- Review 发现问题 → 写入 patterns 文件

## 5. Pivot/Refine 决策（方案失败后的路线选择）

> 适用场景：Codex 连续 3 轮修复失败、方案实现过半发现方向错误

### 决策框架

```
实验/方案执行后，评估结果：

┌─ 结果符合预期 → PROCEED：继续推进
│
├─ 方向对但实现有问题 → REFINE：
│  ├─ 明确哪些部分保留、哪些需要重做
│  ├─ 估算修复成本（时间/行数）
│  └─ 成本可控 → 修复后继续
│     成本过高 → 降级为 P2 或拆分到后续迭代
│
└─ 方向根本性错误 → PIVOT：
   ├─ 记录失败原因（为什么方向错了）
   ├─ 回退到设计阶段
   ├─ 用失败经验指导新方向
   └─ 新方案必须回答：为什么上次失败了？这次如何避免？
```

### PIVOT 时的回退检查清单

- [ ] 是否需要回滚已提交的代码？
- [ ] 已做的部分工作是否有可复用的内容？
- [ ] 失败原因是否已记录到 Lesson Store？
- [ ] 新方向是否已经过 Skeptic 角色质疑？

## 6. SmartPause（高不确定性暂停）

> 适用场景：长任务执行中、多步骤实现中

### 暂停触发条件

| 信号 | 阈值 | 动作 |
|------|------|------|
| 连续失败次数 | ≥ 3 次 | 暂停，等人工判断 |
| Diff 行数 | > 200 行且任务未完成 | 暂停，重新评估范围 |
| 跨模块修改 | ≥ 3 个不同目录 | 暂停，确认影响范围 |
| 需求边界扩大 | 出现原计划外的改动 | 暂停，更新 plan |
| 测试通过但结果异常 | 数值全部相同/为零 | 暂停，语义检查 |

### 暂停时的汇报格式

```
⏸ SmartPause — 高不确定性

**触发原因**: [具体信号]
**当前状态**: [已完成什么、卡在哪里]
**风险**: [如果不暂停继续做，最坏结果是什么]
**建议方案**: [A. 继续 / B. 修复后继续 / C. 回退换方向]

等待人工判断...
```

## 7. CoPilot 介入模式（少量高杠杆节点）

> 适用场景：整个开发流程的人工介入策略

### 高杠杆介入点（必须确认）

1. **需求定义** — 方向是否正确？（避免做错事）
2. **方案评审** — 架构是否合理？（避免返工）
3. **首次测试结果** — 结果是否符合预期？（避免假通过）
4. **合并前 Review** — 最终质量确认（避免引入问题）

### 低杠杆自动放行

- 语法修复 → 自动
- 格式调整 → 自动
- 测试补充 → 自动
- 文档更新 → 自动

### 模式选择

| 场景 | 推荐模式 | 介入次数 |
|------|---------|---------|
| 日常小修小补 | Full-Auto | 0 |
| 单模块功能开发 | Gate-Only | 2-3 |
| 跨模块/复杂功能 | CoPilot | 4-6 |
| 架构级变更 | Step-by-Step | 全程 |
