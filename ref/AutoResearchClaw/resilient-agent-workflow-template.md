# 韧性 Agent 工作流通用模板

> 提炼自 AutoResearchClaw (arxiv 2605.20025) 核心方法论
> 适用场景：任何需要 Claude Code 执行多步骤任务的工作流
> 使用方式：将本模板拆解后嵌入项目的 CLAUDE.md 或 workflow 文档

---

## 架构总览

```
任务输入
   │
   ▼
┌─────────────────────────────────────────────┐
│  静态检查门 (Pre-flight Gate)               │
│  低成本拦截，不消耗执行预算                 │
└──────────────────┬──────────────────────────┘
                   │ 通过
                   ▼
┌─────────────────────────────────────────────┐
│  自愈执行循环 (Self-Healing Loop)           │
│  执行 → 失败签名 → 诊断 → 修复 → 验证      │
│  最多 3 轮，超出触发 Pivot/Refine 决策      │
└──────────────────┬──────────────────────────┘
                   │
          ┌────────┴────────┐
          │                 │
          ▼                 ▼
   ┌─────────────┐   ┌────────────────┐
   │  SmartPause │   │ Pivot / Refine │
   │  高不确定性  │   │  方向决策      │
   │  等待人工   │   │                │
   └─────────────┘   └────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────┐
│  多角色审查 (Multi-Role Review)             │
│  Builder → Skeptic → Architect → 裁决       │
└──────────────────┬──────────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────┐
│  验证注册表 (Verified Registry)             │
│  输出数据 = 唯一真相来源，不可篡改          │
└──────────────────┬──────────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────┐
│  Lesson Store 写入                          │
│  失败签名 + 修复方案 → 持久化经验库         │
└─────────────────────────────────────────────┘
```

## 模块一：静态检查门（Pre-flight Gate）

**作用**：在执行前以低成本拦截明显问题，避免浪费执行预算。

**CC 实现指令**：

```
在执行任何生成/修改任务之前，先完成以下检查。发现问题立即报告，不继续执行：

[ ] 是否存在两个功能完全重复的函数/模块？
[ ] 是否有硬编码的魔法数字或期望值？
[ ] diff 范围是否超出本次任务边界？
[ ] 是否误修改了不该动的文件（配置、锁文件、.gitignore）？
[ ] 任务目标是否足够明确？（不明确则先澄清，不执行）

检查通过后，输出："Pre-flight passed，开始执行。"
```

## 模块二：自愈执行循环（Self-Healing Loop）

**作用**：执行失败后不立即终止，通过结构化诊断寻找根因，最多重试 3 轮。

### 失败签名分类

| 类型 | 描述 | 默认处理 |
|------|------|---------|
| `SYNTAX` | 语法/类型/编译错误 | 直接修复，1 轮内解决 |
| `BOUNDARY` | 边界条件、断言失败 | 诊断业务逻辑，走 Lite 流程 |
| `DEPENDENCY` | 依赖缺失、环境问题 | 考虑调整方案，走 Full 流程 |
| `LOGIC` | 逻辑错误、语义错误 | 回退到设计层，可能触发 Pivot |

### CC 实现指令

```
当测试/执行失败时，执行以下流程（不要立即重试，不要盲目修改）：

## 第 1 步：记录失败签名
输出格式：
- 失败类型: [SYNTAX / BOUNDARY / DEPENDENCY / LOGIC]
- 失败位置: [文件:行号 或 步骤名称]
- 症状: [用户/测试看到的现象]
- 触发条件: [什么输入/状态导致了失败]

## 第 2 步：诊断根因（不是症状）
- 说明为什么会发生这个错误（一句话）
- 确认修复方向后再动手

## 第 3 步：针对性修复
- 只修改与根因直接相关的代码
- 修复后只运行失败的测试，不全量跑

## 第 4 步：记录轮次
- 若 3 轮内未修复 → 停止，输出 SmartPause 格式，等待指令
- 若修复成功 → 将失败签名写入 Lesson Store
```

## 模块三：Pivot / Refine 决策

**作用**：执行 N 轮后仍失败，或发现方向根本性错误时，结构化决策"修还是换"。

### 决策树

```
评估当前状态：

结果符合预期？
└─ 是 → PROCEED：继续推进

方向正确但实现有问题？
└─ 是 → REFINE：
      ├─ 明确保留哪些、重做哪些
      ├─ 估算修复成本
      └─ 成本可控 → 继续
         成本过高 → 降级/拆分到后续迭代

方向根本性错误？
└─ 是 → PIVOT：
      ├─ 记录失败原因（为什么方向错了）
      ├─ 回退到设计/规划阶段
      ├─ 新方案必须回答：上次为何失败？这次如何规避？
      └─ 检查是否需要回滚已提交代码
```

### CC 实现指令

```
连续 3 轮修复失败，或判断当前方向根本性错误时，输出以下格式：

## Pivot/Refine 决策

**当前状态**: [已完成什么，卡在哪里]
**失败原因**: [方向错误 / 实现问题 / 环境问题]
**建议决策**:
  - [ ] PROCEED（继续）
  - [ ] REFINE（修复后继续，预估成本：___）
  - [ ] PIVOT（换方向，回退到：___）

**如果 PIVOT**：
- 失败原因记录：___
- 可复用的已有工作：___
- 新方向初步思路：___

等待确认...
```

## 模块四：SmartPause（高不确定性暂停）

**作用**：自动识别高风险信号，在扩大错误前主动暂停。

### 触发阈值

| 信号 | 阈值 | 严重度 |
|------|------|-------|
| 连续失败次数 | ≥ 3 次 | 高 |
| 改动行数 | > 200 行且任务未完成 | 中 |
| 跨模块/目录修改 | ≥ 3 个不同模块 | 中 |
| 需求边界扩大 | 出现计划外改动 | 高 |
| 结果语义异常 | 输出全部相同/全为零/全为空 | 高 |
| 修改了关键基础设施 | 配置/Schema/接口定义 | 高 |

### CC 实现指令

```
当检测到以下任一信号时，停止执行并输出暂停报告：
- 连续失败 ≥ 3 次
- 本次 diff > 200 行且任务未完成
- 修改了 3 个以上不同目录
- 发现计划外的改动需求
- 输出结果存在语义异常（全零、全相同、全为空）

## ⏸ SmartPause

**触发原因**: [具体信号 + 数据]
**当前进度**: [已完成 X / 总量 Y]
**风险**: [继续执行的最坏结果]
**建议**:
  A. 继续（说明理由）
  B. 先修复 ___ 再继续
  C. 回退，换方向

等待指令...
```

## 模块五：多角色审查（Multi-Role Review）

**作用**：通过角色化视角对代码/方案进行结构化审查，避免单一视角的盲区。

### 角色定义（可按项目调整）

| 角色 | 核心问题 | 适用场景 |
|------|---------|---------|
| **Builder** | 实现是否完整？功能是否可用？ | 所有审查 |
| **Skeptic** | 边界条件？性能隐患？隐式假设？ | 所有审查 |
| **Architect** | 模块耦合？接口契约？可维护性？ | 架构/复杂改动 |

### 审查规模规则

| diff 大小 | 审查方式 |
|-----------|---------|
| ≤ 100 行 | 单轮自检，不需要多角色 |
| 100–200 行 | Builder + Skeptic 双角色 |
| > 200 行 | 三角色完整审查（此类改动应先拆分） |

### CC 实现指令

```
对代码/方案进行审查时，按以下结构输出：

## Builder 视角
- 实现了什么、为何这样设计
- 预期效果和覆盖的场景

## Skeptic 视角（独立评估，不受 Builder 影响）
- 可能的边界条件失败
- 性能/内存/并发风险
- 未处理的错误路径
- 隐式假设（如果输入不符合预期会怎样）

## Architect 视角（仅大改动）
- 是否引入不必要的耦合
- 是否符合项目既有模式
- 接口是否清晰、向后兼容

## 综合裁决
- Builder 与 Skeptic 一致 → 通过
- 有分歧 → 说明用何种方式裁决（测试/数据/规范）
- Skeptic 发现 P0/P1 → 必须修复后重新审查，不得直接合并
```

## 模块六：验证注册表（Verified Registry）

**作用**：确保所有对外输出的数据/结论都有真实运行记录支撑，防止"看起来通过"。

### 核心原则

```
禁止：
❌ "测试通过了"（无具体输出）
❌ "性能提升了"（无前后对比数据）
❌ "Bug 已修复"（无复现→修复的对比记录）
❌ 在报告中使用未经运行的估算数字

要求：
✅ 引用实际运行输出，例如：
   "3 个测试全部通过（耗时 0.8s），输出：[具体 stdout]"
✅ 性能变更必须有前后测量值
✅ Bug 修复必须附复现步骤 + 修复后回归结果
```

### CC 实现指令

```
在输出任何包含数据的结论时：

1. 先运行，再报告——不得在执行前估计结果
2. 保留完整命令输出，报告中引用原始输出片段
3. 完成后做反向校验：
   - 随机抽查 2–3 个关键数值
   - 确认它们来自实际运行记录
   - 不匹配 → 报告必须更正，不得发出
4. UI/视觉变更 → 描述前后差异（截图或 DOM diff）
5. 性能变更 → 附 benchmark 命令 + 完整输出
```

## 模块七：Lesson Store（跨任务经验积累）

**作用**：把每次失败和修复结构化存储，供后续任务检索，避免重复踩坑。

### 存储路径约定

```
.claude/memory/lessons/
├── syntax.md        # 语法/类型错误
├── boundary.md      # 边界条件
├── dependency.md    # 依赖/环境
├── logic.md         # 逻辑/设计错误
└── patterns.md      # 通用模式（Review 发现）
```

### 每条记录格式

```markdown
## [YYYY-MM-DD] [场景简述]

**失败类型**: SYNTAX | BOUNDARY | DEPENDENCY | LOGIC
**症状**: [观察到的现象]
**根因**: [一句话说清楚]
**修复方案**: [具体做法 + 相关 commit/文件]
**教训**: [下次如何避免]
**相关文件**: [路径列表]
**权重衰减**: 写入日期后 7 天高权重，30 天后低权重
```

### CC 实现指令

```
任务开始时：
- Grep .claude/memory/lessons/ 检索与当前任务相关的历史教训
- 优先加载 7 天内的记录，30 天以上仅在直接相关时加载

任务结束时（无论成功/失败）：
- 若发生过失败并修复 → 写入对应主题文件
- 若 Review 发现新问题模式 → 写入 patterns.md
- 若成功且无新教训 → 不写入（保持文件简洁）
```

## 模块八：CoPilot 介入策略

**作用**：明确哪些节点需要人工确认，避免全程审批（效率低）或零审批（质量低）。

### 高杠杆介入点（必须等待确认）

| 节点 | 原因 |
|------|------|
| 任务/需求定义 | 方向错了，后续全部返工 |
| 方案/架构评审 | 结构问题越晚发现越贵 |
| 首次执行结果 | 验证基础假设是否成立 |
| 合并/发布前 | 最终质量门 |

### 自动放行（无需确认）

- 语法修复、格式调整
- 补充测试用例
- 文档/注释更新
- 已有明确规范的重复性操作

### 介入模式选择

| 场景 | 模式 | 介入次数 |
|------|------|---------|
| 日常小修（< 50 行） | Full-Auto | 0 |
| 单模块功能开发 | Gate-Only（3 个关口） | 2–3 |
| 跨模块/复杂功能 | CoPilot（6 个关口） | 4–6 |
| 架构级变更 | Step-by-Step | 全程 |

## 快速组合方案

根据任务类型选择需要激活的模块：

| 任务类型 | 必选模块 | 可选模块 |
|---------|---------|---------|
| 日常 Bug 修复 | 自愈循环、验证注册表 | Lesson Store |
| 新功能开发 | 静态检查门、自愈循环、多角色审查 | SmartPause、CoPilot |
| 架构重构 | 全部模块 | — |
| 自动化长任务 | 静态检查门、自愈循环、SmartPause、验证注册表 | Pivot/Refine |
| Code Review | 多角色审查、验证注册表 | Lesson Store |

## 给 CC 的全局行为规范

将以下内容加入 CLAUDE.md 的行为约束部分：

```markdown
## 韧性执行行为规范

1. **失败不是终点**：任何执行失败，先记录失败签名，再诊断根因，再修复。
   不得在未诊断的情况下盲目重试。

2. **结论必须有证据**：所有报告中的数据必须来自实际运行输出。
   不得使用估算值、预期值或未运行的假设值。

3. **超出边界就停**：diff > 200 行、连续失败 ≥ 3 次、跨 3 个以上模块，
   必须输出 SmartPause，等待指令，不得自行推进。

4. **审查要有分歧**：代码审查不是走形式，Skeptic 角色必须独立评估，
   不得因"看起来没问题"就跳过。

5. **经验要落地**：修复完成后，将失败签名写入 Lesson Store。
   任务开始前，检索相关历史教训。

6. **介入点要明确**：在任务开始时声明本次使用哪种介入模式，
   在高杠杆节点主动暂停等待确认，不得静默推进关键决策。
```
